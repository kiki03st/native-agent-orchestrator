# 검증 범위

## 재시작 후 Codex 검증 (2026-09-16)

- 재시작한 부모 세션에서 정책 주입과 실제 fresh A 작업자의 README 제목·MD 목표 읽기를 확인했습니다. 그러나 자동 예약·바인딩은 생성되지 않았고, 원장은 pending / attempts 0으로 남았습니다. B는 실행하지 않았습니다.
- 로컬 호스트 도구 로그에서 구분자가 없는 `collaborationspawn_agent` 이름을 확인했습니다. 기존 matcher와 핸들러에 이 이름을 추가하고, 예약·바인딩·완료 관측 회귀 테스트가 수정 전 실패하고 수정 후 통과함을 확인했습니다. 로그의 도구 이름이 실제 훅 payload와 동일한지는 아직 확인하지 못했습니다.
- Windows 전체 테스트는 **68 통과, 0 실패, POSIX 1 제외**입니다. 빌드 일치 검사와 갱신한 Codex 설치본의 합성 A → B·MD 검증도 통과했습니다. Claude 경로의 자동 회귀 테스트는 통과했으며 Claude 실사용은 사용자 요청으로 보류했습니다.
- Codex 설치본과 훅 신뢰 설정을 갱신한 뒤 실제 A를 다시 확인했지만 자동 기록은 여전히 없었습니다. 추가 관리 위임은 중단했습니다. 현재 세션의 설정 보유 여부 또는 호스트의 도구 이벤트 전달 문제가 원인인지는 미확정이며, 재시작만으로 해결된다고 판단하지 않습니다. 수동 예약·바인딩으로 성공 기록을 만들지 않았습니다.

## Codex 실사용 장애 조사·설정 복구 (2026-09-16)

- 사용자가 Claude 실사용 검증을 보류해 Codex만 진행했습니다.
- 설치된 Codex의 공식 로컬 프로토콜 스키마를 생성하고, 모델 세션을 만들지 않는 진단 프로세스에서 `hooks/list`를 조회했습니다. 기존 orchestrator 훅 4개가 모두 `enabled:false`, `trustStatus:modified`인 것을 확인했습니다.
- 같은 훅에 대한 Windows 경로 표기 중복과 오래된 신뢰 상태를 백업 후 정리했습니다. 실제 호스트가 반환한 현재 hash로 승인된 설치본의 신뢰를 갱신했으며, 두 Codex 사용자 범위 모두 4개 훅이 `enabled:true`, `trustStatus:trusted`, 로딩 오류 0개로 확인됐습니다.
- 복구 후 실제 fresh worker가 README 첫 제목을 읽고 완료했습니다. 네이티브 `thread/list`에서 부모·agent_path를 대조하고 해당 rollout의 `turn_context`와 `task_complete`를 확인해 실제 `gpt-5.6-sol / high` 실행 근거를 확보했습니다. 진단용 로컬 app-server는 기존 기록을 읽었으며 작업자를 생성하지 않았습니다.
- 실행 중인 기존 부모 세션에서는 여전히 자동 예약·바인딩이 없었습니다. 기존 세션이 이전 훅 설정을 보유하는지는 아직 확정하지 않았습니다. 이 대화를 재시작·재개한 뒤 훅 활성과 A → B 자동 실행을 다시 확인해야 합니다. 수동으로 예약·바인딩을 채워 성공 처리하지 않았습니다.

## 추가 테스트 설계·실행 (2026-09-16)

[테스트 케이스와 판정](test-cases.md)에 정상·오류·동시성·배포·실사용 조건을 정리했습니다. 배포 테스트를 세 호스트 계약의 MD 포함 2단계 체인으로 확장하고, 잘못된 상태 갱신의 데이터 보존 및 새 프로세스 재개 테스트를 추가했습니다. Windows 67개 통과·POSIX 1개 제외, WSL Ubuntu 24.04는 68개 모두 통과했습니다. 제품 코드는 변경하지 않았습니다. 실제 호스트 연동의 미검증 항목은 자동 테스트와 별도로 남아 있습니다.

## 맥락 관리·호스트 계약 변경 검증 (2026-09-16)

- Windows 전체 테스트: 64개 통과, 실패 0개, POSIX 권한 검사 1개 제외. 기존 Claude 경로와 Codex legacy 경로를 포함합니다.
- 신규 Codex collaboration 계약의 정확한 인자, 네이티브 task 이름 바인딩, 완료와 종료의 구분, 실제 모델 근거 요구, 오래된 결과·재시도·의존 관계를 확인했습니다.
- MD의 실행별·DB별 분리, 부모 소유권, 오래된 수정본 거부, 동시 갱신, 빈 목록·한글 왕복, 크기 제한, 잘못된 기록 거부를 확인했습니다. 독립 검토에서 발견한 한글 바이트 크기 문제를 수정했습니다.
- `npm run check:build`, `git diff --check`, Claude 플러그인·marketplace 검증을 통과했습니다.
- Codex 기존 수동 설치본과 두 사용자 설정 범위를 갱신했습니다. Claude는 로컬 marketplace의 사용자 플러그인으로 설치하고 기존 수동 orchestrator 훅 6개를 제거했습니다. 다른 훅은 보존하고 기존 설정과 스크립트를 비공개 위치에 백업했습니다.
- 두 설치본의 소스 일치, 실제 설치 matcher, MD, 읽기 전용 2단계 의존 실행을 **합성 이벤트로 재현**했습니다. 이는 실제 호스트의 자동 동작 증명이 아닙니다.
- 현재 Codex 세션에서 실제 fresh worker가 README 첫 제목을 읽고 완료했습니다. 그러나 SQLite에 자동 예약·바인딩 이벤트가 생기지 않았고, 실제 실행 모델 메타데이터도 제공되지 않았습니다. 후속 단계는 실행하지 않았습니다. 현재 세션의 관리 위임 활성화는 검증되지 않았습니다.
- Claude의 새 플러그인 설정은 설치·검증했으나 이 Codex 세션에서 실제 Claude Agent 실행을 관측하지 못했습니다. 별도 CLI/API 작업자를 대체 수단으로 사용하지 않았습니다. 두 호스트 모두 새 세션에서 훅 로딩·신뢰와 실제 모델을 확인한 뒤 2단계 실사용 검증이 필요합니다.

## 이전 배포 검증

개발 환경: Windows 및 WSL Ubuntu 24.04, Node.js 24.18.0, Codex CLI 0.154.0, Claude Code 2.1.270.

배포 전에 확인한 항목:

- 공통 엔진·수명 주기·Claude 어댑터 회귀 테스트.
- 두 개의 설치 사본이 설치 폴더 밖 공통 사용자 데이터 위치를 선택하는지 확인.
- 공백이 포함된 다른 임시 경로로 두 배포판을 복사한 뒤 실제 훅 명령을 실행하고, 예약 → 바인딩 → 결과 검증 → 종료 이벤트를 재현.
- Claude의 namespaced 작업자 선택, 실제 배포된 프로필 읽기, 중지 관측만으로 선행 단계가 종료되지 않는지 확인.
- Codex manifest 검증, Claude manifest/marketplace/18개 agent 정의 검증.
- 독립 코드 검토에서 지적한 Codex 추가 인자 허용을 거부하도록 보강하고 회귀 테스트로 검증.
- Ubuntu에서 POSIX 권한 문제를 수정 전 재현하고, 새 데이터 폴더 0700 및 DB/WAL/SHM 파일의 사용자 전용 접근을 수정 후 확인. Windows에서는 해당 POSIX 검사를 건너뜁니다.
- 빌드 결과와 공통 소스 일치 여부, Git 변경의 공백 오류, 배포 목록의 개인 경로·인증 파일·실행 기록 제외 여부.

이 테스트는 실제 모델 서비스를 호출하지 않습니다. 호스트가 훅을 로딩하고 실제 Agent/spawn_agent 호출을 이벤트로 전달하는지는 설치 대상의 새 세션에서 별도 확인해야 합니다. 특히 일부 래퍼 도구 경로는 네이티브 호출을 훅에 노출하지 않을 수 있습니다. `prepare` 이후 실제 호출에도 예약이 생성되지 않는다면 관리 위임이 활성화되었다고 간주하지 마세요. 해당 호출 경로로 계속 실행하지 말고 호스트 통합 상태를 확인해야 합니다.

이 저장소를 만들면서 기존 사용자 훅을 플러그인 설치로 교체하거나 새 플러그인을 중복 활성화하지 않았습니다. 따라서 배포 형식·재현 테스트 통과와 실제 사용자 환경으로의 이전 완료는 별개입니다. Linux/macOS는 GitHub Actions 결과를 확인하세요.
